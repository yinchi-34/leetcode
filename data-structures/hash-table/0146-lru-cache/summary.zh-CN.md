## 2. 题意理解（Problem Understanding）

设计一个容量为 `capacity` 的缓存，存放键值对，支持两个操作：

- `get(key)`：键在缓存中时返回它的值，否则返回 `-1`。
- `put(key, value)`：键已存在时更新它的值；否则插入这个键值对。插入后若键的个数超过容量，就淘汰**最久未使用**的键。

一次 `get` 命中或一次 `put` 都算“使用”了这个键。两个操作都要求平均 $`O(1)`$ 时间。

**示例**

- 输入：`["LRUCache","put","put","get","put","get","put","get","get","get"]`，参数 `[[2],[1,1],[2,2],[1],[3,3],[2],[4,4],[1],[3],[4]]`
- 输出：`[null,null,null,1,null,-1,null,-1,3,4]`

过程：容量为 2。放入 1、2 后，`get(1)` 让 1 变成最近使用，所以放入 3 时淘汰的是 2；之后放入 4 时，最久未使用的是 1，淘汰 1，缓存剩下 3、4。

**关键要求**

1. 约束（来自力扣题面）：$`1 \le \mathrm{capacity} \le 3000`$，$`0 \le \mathrm{key} \le 10^4`$，$`0 \le \mathrm{value} \le 10^5`$，至多 $`2 \times 10^5`$ 次调用。
2. `get` 和 `put` 都要求平均 $`O(1)`$ 时间，所以不能每次扫描全部键来找最久未使用的那个。
3. 边界：容量为 1 时每次插入新键都会淘汰旧键；`put` 一个已存在的键只更新值和使用顺序，不淘汰；`get` 未命中不改变任何键的使用顺序；值可以是 0，所以不能用 0 表示“不存在”。

## 3. 初始思路（Initial Approach）

本节依据原始 Python 实现及其代码注释整理。仓库中的 [solution.go](./solution.go) 是这份实现的 Go 改写，结构、函数划分和操作顺序都与原实现一致：`DLinkedNode` 对应 `dLinkedNode`，`_remove`、`_add_to_head` 对应 `remove`、`addToHead`。

### 第一次想到：散列表 + 双向链表，并加头尾哨兵

- 用字典 `cache` 从键找到结点，用双向链表维护使用顺序，头部是最近使用、尾部是最久未使用。
- 注释写明加哨兵的目的是“减少判断”：`head` 和 `tail` 两个哑结点始终在链表两端，插入和删除都不用判断空指针。
- `get`：命中时“首先需要删除当前节点，再放到头节点”，即先 `_remove` 再 `_add_to_head`。
- `put`：键已存在时更新 `value` 再移到头部；否则新建结点，先写入字典并插到头部，再检查是否超过容量，超过就删除尾部结点。

### 关键点：插入表头时指针的修改顺序

注释中记录的关键点：插入时涉及 `head`、`A`、`B` 三个结点，`A` 是要插入的结点，`B` 是原来的第一个结点。先把 `A` 的 `prev` 和 `next` 设好；之后“一定要先修改 B 的节点，再去修改 `head.next`”。原因见[难点三](#难点三插入表头时为什么要先改-bprev)。

## 4. 算法表达（Algorithm Specification）

**算法名称：** 散列表 + 带头尾哨兵的双向链表（Hash Map with Head and Tail Sentinel Doubly Linked List）

### 4.1 输入（Input）

容量 $`c \ge 1`$，以及按时间顺序给出的操作序列

```math
O = \langle o_1, o_2, \ldots, o_q \rangle
```

满足：

- 每个 $`o_t`$ 是 $`\mathrm{GET}(k)`$ 或 $`\mathrm{PUT}(k, v)`$，其中 $`k`$、$`v`$ 是非负整数。
- $`t`$ 同时作为第 $`t`$ 个操作发生的时刻，不同操作的时刻互不相同。

### 4.2 输出（Output）

先把题目中的 LRU 语义写成精确的抽象规格。设执行完前 $`t`$ 个操作后，缓存中的键集合为 $`K_t`$（$`K_0 = \varnothing`$），每个 $`k \in K_t`$ 有当前值 $`\mathrm{val}_t(k)`$ 和**最近使用时刻** $`\mathrm{last}_t(k)`$，即 $`k`$ 最后一次被 GET 命中或被 PUT 的时刻。第 $`t`$ 个操作的效果为：

- $`\mathrm{GET}(k)`$，$`k \notin K_{t-1}`$：返回 $`-1`$，状态不变。
- $`\mathrm{GET}(k)`$，$`k \in K_{t-1}`$：返回 $`\mathrm{val}_{t-1}(k)`$，令 $`\mathrm{last}_t(k) = t`$，其余不变。
- $`\mathrm{PUT}(k, v)`$，$`k \in K_{t-1}`$：令 $`\mathrm{val}_t(k) = v`$、$`\mathrm{last}_t(k) = t`$，键集合不变。
- $`\mathrm{PUT}(k, v)`$，$`k \notin K_{t-1}`$：若 $`\lvert K_{t-1} \rvert = c`$，先删去 $`\mathrm{last}`$ 最小的键（最久未使用）；再加入 $`k`$，令 $`\mathrm{val}_t(k) = v`$、$`\mathrm{last}_t(k) = t`$。

因为每个时刻至多使用一个键，$`K_{t-1}`$ 中各键的 $`\mathrm{last}`$ 互不相同，“$`\mathrm{last}`$ 最小的键”是唯一的。

输出必须满足：

- 每个 GET 操作返回的值与上面的规格一致。
- 由规格的最后一种情况可知，始终有 $`\lvert K_t \rvert \le c`$。

### 4.3 伪代码（Pseudocode）

本题不按下标访问数组，伪代码中没有索引。`head` 与 `tail` 是两个不存数据的哨兵：`head.next` 是最近使用的结点，`tail.prev` 是最久未使用的结点。

```text
CONSTRUCTOR(c)
    head.next ← tail
    tail.prev ← head
    M ← empty hash map             // 键 → 结点
    cap ← c

GET(k)
    x ← SEARCH(M, k)
    if x = NIL
        return -1
    REMOVE(x)
    ADD-TO-HEAD(x)
    return x.value

PUT(k, v)
    x ← SEARCH(M, k)
    if x ≠ NIL                      // 键已存在：只更新，不淘汰
        x.value ← v
        REMOVE(x)
        ADD-TO-HEAD(x)
        return
    x ← new node with key k, value v
    INSERT(M, k, x)
    ADD-TO-HEAD(x)
    if |M| > cap                    // 超过容量：淘汰表尾
        y ← tail.prev
        REMOVE(y)
        DELETE(M, y.key)

REMOVE(x)                           // 从链表中摘下 x
    x.prev.next ← x.next
    x.next.prev ← x.prev

ADD-TO-HEAD(x)                      // 把 x 插到 head 之后
    x.prev ← head
    x.next ← head.next
    head.next.prev ← x              // 先改原第一个结点 B
    head.next ← x                   // 再改 head.next
```

**状态定义**

- `head`、`tail`：对应代码中的同名字段，两个哨兵结点，始终位于链表两端。
- `M`：对应 `cache`，从键到链表结点的散列表。
- `cap`：对应 `capacity`。
- 结点 `x`：对应 `dLinkedNode`，存 `key`、`value`、`prev`、`next`。存 `key` 是为了淘汰表尾结点时能从 `M` 中删掉对应的键。

代码中 `remove`、`addToHead` 分别对应 `REMOVE`、`ADD-TO-HEAD`。`GET` 直接返回表达式，没有结果变量。

### 4.4 正确性（Correctness）

**证明方法：表示不变式 + 对操作个数归纳**

#### 一、正确性依赖的关键条件

记链表从 `head.next` 出发沿 `next` 走到 `tail` 之前经过的结点依次为 $`x_1, x_2, \ldots, x_s`$（$`s = 0`$ 表示空表）。

算法正确性依赖于：

1. **散列表的字典语义**（CLRS §11.2）：`SEARCH`、`INSERT`、`DELETE` 正确地实现了从键到结点的映射。
2. **链表操作的局部性**：`REMOVE` 只改 `x` 前后两个结点的指针，把 $`x`$ 从序列中去掉，其余结点的相对顺序不变；`ADD-TO-HEAD` 把 $`x`$ 放到序列最前面，其余结点顺序不变。因为 `head` 和 `tail` 始终在两端，任何真实结点都有非空的前驱和后继，表空、只有一个结点、`x` 是第一个或最后一个结点时都不需要特判（与 CLRS §10.2 用哨兵消除边界的做法相同）。
3. **最近使用时刻互不相同**：抽象规格中各键的 $`\mathrm{last}`$ 两两不同，所以按 $`\mathrm{last}`$ 排序是唯一的，“最久未使用的键”也是唯一的。

这三条把问题化为：只要链表顺序始终与 $`\mathrm{last}`$ 的降序一致，表尾就是该淘汰的键。

#### 二、正确性证明

**表示不变式（Representation Invariant）**

执行完前 $`t`$ 个操作后，以下四条同时成立：

**不变式 I：链表结构完好**

`head`、$`x_1, \ldots, x_s`$、`tail` 依次构成一个双向链表：`head.next.prev = head`，`tail.prev.next = tail`，且对每个 $`x_i`$ 都有 `x_i.next.prev = x_i`、`x_i.prev.next = x_i`。

**不变式 II：散列表与链表一一对应**

$`x_1, \ldots, x_s`$ 的键两两不同，且 $`\{x_1.\mathrm{key}, \ldots, x_s.\mathrm{key}\} = K_t`$；`M` 的键集合也恰为 $`K_t`$，并且对每个 $`k \in K_t`$，`M[k]` 就是链表中键为 $`k`$ 的结点。特别地，$`s = \lvert M \rvert = \lvert K_t \rvert`$。

**不变式 III：值正确**

对每个 $`i`$，$`x_i.\mathrm{value} = \mathrm{val}_t(x_i.\mathrm{key})`$。

**不变式 IV：链表按最近使用时刻降序排列**

```math
\mathrm{last}_t(x_1.\mathrm{key}) > \mathrm{last}_t(x_2.\mathrm{key}) > \cdots > \mathrm{last}_t(x_s.\mathrm{key})
```

即表头是最近使用的键，表尾 $`x_s`$ 是最久未使用的键。

**初始化（Initialization）**

$`t = 0`$ 时，`CONSTRUCTOR` 令 `head.next = tail`、`tail.prev = head`，链表为空；`M` 为空；$`K_0 = \varnothing`$。四条不变式都成立（II、III、IV 对空表平凡成立）。

**保持（Maintenance）**

假设前 $`t-1`$ 个操作后不变式成立，考虑第 $`t`$ 个操作。由不变式 II，`SEARCH(M, k)` 返回非 NIL 当且仅当 $`k \in K_{t-1}`$，且返回的就是链表中键为 $`k`$ 的结点 $`x = x_j`$。

- **情况一：GET 未命中（$`k \notin K_{t-1}`$）**。算法返回 $`-1`$，不修改任何结构；规格同样返回 $`-1`$ 且状态不变。不变式保持。
- **情况二：GET 命中（$`k = x_j.\mathrm{key}`$）**。由不变式 III，返回的 `x.value` 等于 $`\mathrm{val}_{t-1}(k)`$，与规格一致。`REMOVE` 再 `ADD-TO-HEAD` 把序列变为 $`x_j, x_1, \ldots, x_{j-1}, x_{j+1}, \ldots, x_s`$，结点集合不变，所以 I、II 保持，值没变，III 保持。规格令 $`\mathrm{last}_t(k) = t`$，比所有其他键的 $`\mathrm{last}`$ 都大，其余键的 $`\mathrm{last}`$ 和相对顺序都不变，所以新序列仍按 $`\mathrm{last}_t`$ 降序，IV 保持。
- **情况三：PUT 已存在的键（$`k = x_j.\mathrm{key}`$）**。算法把 $`x_j.\mathrm{value}`$ 改为 $`v`$ 并移到表头，不淘汰。规格中键集合不变，$`\mathrm{val}_t(k) = v`$，$`\mathrm{last}_t(k) = t`$。III 对 $`x_j`$ 成立，对其他结点不受影响；I、II、IV 的论证同情况二。
- **情况四：PUT 新键（$`k \notin K_{t-1}`$）**。算法先插入、再按需淘汰，与规格“先淘汰、再插入”的写法顺序不同，下面证明两者结果相同。
  - *插入*：新建结点 $`x_0`$ 存 $`k`$ 和 $`v`$，令 `M[k]` 指向它并插到表头，序列变为 $`x_0, x_1, \ldots, x_s`$。$`k`$ 原来不在 $`K_{t-1}`$ 中，所以链表中的键仍两两不同，且链表与 `M` 的键集合都变为 $`K_{t-1} \cup \{k\}`$，大小为 $`s + 1`$；新结点的值为 $`v`$；把 $`k`$ 的最近使用时刻记为 $`t`$，它大于所有其他键，位于表头，序列仍按最近使用时刻降序；I 由关键条件 2 保持。
  - *淘汰*：由不变式 II 得 $`s = \lvert K_{t-1} \rvert \le c`$，所以 $`\lvert M \rvert = s + 1 > c`$ 当且仅当 $`\lvert K_{t-1} \rvert = c`$，这正是规格要求淘汰的条件。此时 $`s = c \ge 1`$，表中至少有 $`x_0`$ 和 $`x_s`$ 两个真实结点，`tail.prev` 是 $`x_s`$ 而不是新结点 $`x_0`$。由不变式 IV（对 $`K_{t-1}`$），$`x_s`$ 正是 $`K_{t-1}`$ 中最久未使用的键，也就是规格删去的键。算法摘下 $`x_s`$，再用 $`x_s`$ 中保存的键从 `M` 中删除，链表和 `M` 同时少了这个键，剩下 $`x_0, x_1, \ldots, x_{s-1}`$，键集合恰为规格的 $`K_t`$。若 $`s < c`$，规格与算法都不淘汰，键集合为 $`K_{t-1} \cup \{k\} = K_t`$。
  - 两种情形下 I～IV 对 $`K_t`$ 都成立：II 由键集合相等得到，III 中新结点的值为 $`v = \mathrm{val}_t(k)`$，IV 是降序序列去掉末尾元素后仍为降序。

因此，不变式在第 $`t`$ 个操作后继续成立。

**终止（Termination）**

每个操作只执行常数条语句，没有循环，所以每个操作都会终止。对 $`t = q`$ 归纳完成后，由情况一、二，每个 GET 的返回值都与抽象规格一致；由不变式 II 和情况四的淘汰条件，每个操作结束时都有 $`\lvert M \rvert \le c`$（只在 PUT 新键的插入与淘汰之间短暂为 $`c + 1`$）。

#### 三、结论

不变式 IV 让“最久未使用的键”恒等于表尾，不变式 II 让任何键都能经散列表直接拿到它的结点。于是 LRU 规格要求的三件事（按键取值、把某个键标为最近使用、淘汰最久未使用的键）分别化为一次散列表查找、一次 `REMOVE` 加 `ADD-TO-HEAD`、一次摘除表尾，算法对所有合法的操作序列都给出与规格一致的结果。

实现上有三个顺序不能颠倒：`Put` 先判断键是否已存在，再插入和淘汰，否则更新已有键会被当成新键处理（违反情况三）；`ADD-TO-HEAD` 必须先改原第一个结点的 `prev` 再改 `head.next`（见[难点三](#难点三插入表头时为什么要先改-bprev)）；淘汰时用表尾结点里保存的键删散列表条目，代码中 `delete(c.cache, lru.key)` 用的就是刚摘下结点里的键。

### 4.5 复杂度分析（Complexity Analysis）

设容量为 $`c`$，操作个数为 $`q`$。下面的“期望”指散列表单次操作的期望 $`O(1)`$ 时间（见[总体笔记 §2.1](../README.zh-CN.md)）。

**时间复杂度：每个操作期望 O(1)，共期望 O(q)**

- `GET`：一次散列表查找，命中时再做一次 `REMOVE` 和一次 `ADD-TO-HEAD`，共改写常数个指针，最坏 $`O(1)`$。
- `PUT`：一次查找；已存在时同 `GET`；新键时一次散列表插入、一次插入表头，至多再加一次摘除表尾和一次散列表删除。

链表部分每个操作最坏 $`O(1)`$，散列表部分期望 $`O(1)`$，所以每个操作期望 $`O(1)`$，$`q`$ 个操作共期望 $`O(q)`$。若散列严重冲突，单次散列表操作可能退化为 $`\Theta(c)`$；Go 运行时为每个 `map` 使用随机散列种子，输入无法刻意制造这种情况。

**空间复杂度：O(c)**

由不变式 II，链表中至多 $`c`$ 个真实结点、`M` 中至多 $`c`$ 个条目（PUT 新键时短暂为 $`c + 1`$），另有两个哨兵结点，额外空间 $`O(c)`$。这里按存活的结点和条目计；Go `map` 删除条目后不会把已分配的空间还给系统，具体内存布局由运行时决定，不在此展开。

## 5. 思维难点（Learning Notes）

### 难点一：为什么要两种结构，单用一种不行吗？

LRU 缓存同时要回答两类问题：“键 $`k`$ 的结点在哪里”和“谁是最久未使用的键”，并且要能把任意一个键挪到“最近使用”的位置。

**理解过程**

逐个排除单一结构：

- 只用散列表：能 $`O(1)`$ 按键查找，但散列表不维护顺序，找最久未使用的键要扫描全部键，$`O(c)`$。
- 只用链表：顺序有了，但按键查找要从头走，$`O(c)`$。
- 用切片按使用顺序存键：把中间某个键挪到末尾要搬移后面的元素，$`O(c)`$。

组合起来时，散列表的值不存“值”，而是存**链表结点的指针**。这样一次散列表查找就直接落到链表中的位置，链表在已知结点的前提下摘除、插入都是 $`O(1)`$。两种结构各管一类查询，指针把它们连在一起。

**可迁移思维：** 当一个结构要同时支持“按键定位”和“按顺序定位”两种访问方式，而单一结构只擅长其中一种时，可以用两个结构分别负责，并让一个结构存另一个结构中元素的“位置”（指针或下标）。代价是每次修改都要同时维护两边的一致性，这正是表示不变式要证明的内容。

### 难点二：为什么必须是双向链表，结点里为什么还要存键？

**理解过程**

- **双向**：从链表中摘下结点 $`x`$ 要修改它前一个结点的 `next`。单向链表里没有 `prev`，只能从表头找前驱，退化为 $`O(c)`$。CLRS §11.2 在讨论链接法删除时也指出：给定元素本身（而不是关键字）时，双向链表能在 $`O(1)`$ 时间内删除它。本题的散列表正是用来把“关键字”换成“元素本身”的。
- **结点存键**：淘汰时我们从链表这一侧拿到表尾结点，接着要删掉散列表中指向它的条目，必须知道它的键。如果结点只存值，就无法从链表回到散列表。
- **哨兵**：没有哨兵时，表空、只有一个结点、摘除第一个或最后一个结点都要判断 `nil`。加上 `head`、`tail` 两个哨兵后，最近使用的是 `head.next`，最久未使用的是 `tail.prev`，所有真实结点都有前驱和后继，`REMOVE` 与 `ADD-TO-HEAD` 不需要任何分支。CLRS §10.2 用一个循环哨兵 `L.nil` 同时充当头尾，效果相同，只是少一个结点。

**可迁移思维：** 两个结构互相引用时，要检查两个方向的导航是否都能 $`O(1)`$ 完成：从散列表到链表靠存指针，从链表回到散列表靠结点里存键。缺了任意一个方向，某个操作就会退化。

### 难点三：插入表头时，为什么要先改 B.prev？

这是原始实现的代码注释中记下的重点：插入 `A` 时涉及 `head`、`A`、`B` 三个结点，`B` 是原来的第一个结点，“一定要先修改 B 的节点，再去修改 `head.next`”。

**理解过程**

在 `ADD-TO-HEAD` 里，`B` 没有单独的变量保存，代码是经由 `head.next` 找到它的（第三句写的是 `head.next.prev`）。如果先执行 `head.next ← A`，再执行 `head.next.prev ← A`，第二句里的 `head.next` 已经是 `A`，于是变成 `A.prev ← A`：`A` 的前驱指向自己，`B.prev` 仍指向 `head`。链表从此断开，之后摘除 `A` 或 `B` 都会改错指针。

可以用测试验证：把 Go 代码中这两句对调后，`go test` 立即失败，因为测试在每次调用后都检查不变式 I，而 `A.prev = A` 违反了 `A.prev.next = A`。

**可迁移思维：** 改指针时，先问“哪个结点只能经由即将被覆盖的指针找到”，先处理它，再覆盖那个指针。另一种写法是先用临时变量保存 `B := head.next`，之后的赋值顺序就不再要紧。

### 难点四：`Put` 中先判断存在，再插入、再淘汰

**理解过程**

`Put` 先判断键是否已存在：已存在时只更新值和顺序，不涉及容量。若反过来先按容量淘汰，缓存已满时更新已有键会先淘汰表尾，淘汰掉一个本不该淘汰的键。测试中的“Updating an existing key does not evict”专门覆盖这个分支。

对新键，这份实现先插入、再在 `len(cache) > capacity` 时淘汰表尾，而不是先在 `len(cache) == capacity` 时淘汰再插入。两种写法结果相同（情况四的证明），但先插入的写法要确认一件事：被淘汰的不会是刚插入的结点。新结点在表头，而超过容量时表中有 $`c + 1 \ge 2`$ 个结点，表尾一定是另一个结点。代价是 `cache` 会短暂多出一个条目，所以 Go 代码用 `make(map[int]*dLinkedNode, capacity+1)` 预分配。

**可迁移思维：** 设计题中，“更新已有元素”和“插入新元素”常常走不同的分支，容量、计数之类的约束只在插入新元素时才变化。写代码前先把规格按“键是否已存在”分情况列清楚，再决定判断顺序；若改变“插入”和“淘汰”的先后，要检查边界上被淘汰的是否仍是规格要求的那个元素。

## 6. 可迁移知识（Key Takeaways）

本题总结出以下可复用的方法：

1. **Hash Map to Node Pointer（散列表存结点指针）**：在本题中 `M[k]` 直接给出链表结点，把“按键找结点”降到期望 $`O(1)`$。适用于需要给某个有序结构（链表、堆、数组）补一个按键索引的设计题，例如 LFU 缓存、$`O(1)`$ 插入删除并随机取元素。限制是每次修改都要同时更新两边，且只有期望 $`O(1)`$。
2. **Doubly Linked List with Sentinel（带哨兵的双向链表）**：在本题中提供已知结点时 $`O(1)`$ 的摘除与插入表头，并用 `tail.prev` 直接拿到最久未使用的结点。适用于需要在序列任意位置删除、并在端点插入的场景。成立条件是调用方已经持有结点指针；若只知道值，仍要先查找。
3. **Recency Order as Move-to-Front（以“移到最前”维护最近使用顺序）**：每次使用就把元素移到表头，表头到表尾即按最近使用时刻降序（不变式 IV）。适用于 LRU 一类“按最后一次访问时间排序”的问题；若排序依据是访问次数（LFU），只移到表头不够，需要按次数分桶。
4. **Representation Invariant（表示不变式）**：在本题中把“链表与散列表一致、链表按最近使用时刻降序”写成不变式，对操作个数归纳证明。适用于所有设计类数据结构题：先写出抽象规格，再写出具体结构满足的不变式，最后逐个操作、逐个分支证明不变式保持且返回值符合规格。

Go 标准库的 `container/list` 是带单个哨兵的循环双向链表，`MoveToFront`、`Remove`、`PushFront`、`Back` 正好对应本题用到的链表操作。本解法沿用原始实现手写链表，每一步指针改写都能和伪代码、证明对上。

**一句话总结**

散列表负责“按键找到结点”，带头尾哨兵的双向链表负责“按最近使用顺序排列并 $`O(1)`$ 挪动”，结点存键让两边能互相找到，于是 `get` 和 `put` 都是期望 $`O(1)`$。
